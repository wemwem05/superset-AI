# Comeback Leads Dashboard — Аналитика возвратных лидов

## Источник данных

Таблица `dash.leads_comebacks` — пользователи, которые установили приложение, но не купили абонемент, и получили comeback-оффер (возвратное предложение).

| Поле | Тип | Описание |
|------|-----|----------|
| country | text | Страна |
| offer_id | int | ID оффера |
| user_id | int | ID пользователя |
| offer_date | date | Дата оффера |
| send_to_amocrm | bool | Был ли передан в AmoCRM |
| send_to_amocrm_date | date | Дата передачи в AmoCRM |
| purchase_date | date | Дата первой покупки (окно 5 дней) |
| days_to_purchase | int | Дней от оффера до покупки |
| purchase_price | numeric | Сумма покупки |
| days_from_reg | int | Дней от регистрации до получения оффера |
| gender | text | Пол |
| user_age | numeric | Возраст |
| city | text | Город |
| device_type | text | Тип устройства |

**Окно конверсии:** 5 дней от оффера.

## Структура дэшборда

### Tab 1: Overview — Общая эффективность comeback-механики

Главный вопрос: **работает ли comeback-оффер и насколько он эффективен?**

**KPI-карточки (Big Number):**
1. **Всего офферов** — COUNT(offer_id) за период. Масштаб работы с возвратной аудиторией.
2. **Конверсия в покупку (CR %)** — COUNT(purchase_date) / COUNT(offer_id). Главная метрика эффективности.
3. **Средний чек** — AVG(purchase_price) WHERE purchase_date IS NOT NULL. Монетизация возвратной аудитории.
4. **Общая выручка** — SUM(purchase_price). Вклад comeback-канала в бизнес.
5. **Медианное время до покупки** — PERCENTILE_CONT(0.5) по days_to_purchase. Скорость принятия решения.
6. **Доля переданных в CRM** — COUNT(send_to_amocrm = true) / COUNT(*). Покрытие CRM-обработкой.

**Графики:**

1. **Тренд офферов и конверсий по дням/неделям** — dual-axis line chart: количество офферов (bars) + CR % (line).
   - *Проблема, которую решает:* отслеживание динамики — растёт ли поток камбэков, не деградирует ли конверсия. Позволяет быстро заметить аномалии: если объём вырос, а CR упал — возможно, снизилось качество офферов или изменились критерии попадания в когорту.

2. **Выручка по неделям** — bar chart, SUM(purchase_price) по неделям.
   - *Проблема:* оценка финансового вклада comeback-канала во времени. Помогает обосновать инвестиции в канал перед руководством.

3. **CR по месяцам — тренд** — line chart, CR по месяцам за последние 12 месяцев.
   - *Проблема:* сезонность и долгосрочные тренды. Есть ли месяцы, когда камбэки конвертятся лучше (например, начало года — сезон «новой жизни»)?

### Tab 2: CRM-эффективность — AmoCRM impact

Главный вопрос: **даёт ли передача лида в CRM uplift в конверсии?**

**Графики:**

1. **CR: отправленные в AmoCRM vs не отправленные** — grouped bar chart. Два столбца: send_to_amocrm = true / false, метрика — CR %.
   - *Проблема:* ключевой вопрос для CRM-команды — есть ли вообще смысл в ручной обработке? Если CR у переданных в CRM значимо выше — это аргумент за расширение CRM-команды. Если разница минимальна — возможно, автоматизированный оффер достаточен.

2. **Тренд CR по CRM-статусу по неделям** — line chart, две линии (CRM / не CRM).
   - *Проблема:* стабильность uplift'а. Если разрыв между линиями сужается — CRM-процесс деградирует (например, перегруженные менеджеры хуже обрабатывают лиды).

3. **Задержка передачи в CRM** — histogram, DATEDIFF(send_to_amocrm_date, offer_date) для send_to_amocrm = true.
   - *Проблема:* скорость реакции CRM-команды. Если лид передаётся на 2-3 день из 5-дневного окна — остаётся слишком мало времени на конверсию. Помогает установить SLA для передачи.

4. **CR vs задержка передачи в CRM** — bar chart: группы по дням задержки (0, 1, 2, 3, 4, 5), метрика — CR %.
   - *Проблема:* каждый день задержки стоит конверсии. Этот чарт даёт конкретную цифру: «передача в день оффера даёт CR X%, задержка на 2 дня — CR Y%». Мощный аргумент для ускорения процесса.

5. **Средний чек: CRM vs не CRM** — Big Number пара.
   - *Проблема:* CRM-менеджеры могут продавать более дорогие абонементы (upsell). Если средний чек у CRM-лидов выше — это дополнительная ценность CRM-обработки помимо CR.

6. **Объём и CR по CRM-статусу по городам** — table: city, total offers, CRM count, CRM %, CR (CRM), CR (no CRM), uplift.
   - *Проблема:* приоритизация CRM-ресурсов по географии. В каких городах CRM-обработка даёт максимальный uplift? Ограниченных менеджеров стоит направлять именно туда.

### Tab 3: Неактивность и тайминг — когда возвращать?

Главный вопрос: **через какое время после регистрации comeback-оффер работает лучше всего?**

**Графики:**

1. **Распределение days_from_reg** — histogram с бакетами (0-30, 31-60, 61-90, 91-180, 181-365, 365+).
   - *Проблема:* понимание профиля аудитории — это «свежие» потери (ушли в первый месяц) или давно забывшие о приложении пользователи? Определяет стратегию коммуникации.

2. **CR по когортам неактивности (days_from_reg)** — bar chart, те же бакеты, метрика — CR %.
   - *Проблема:* самый критичный вопрос для тайминга. Если пользователи с days_from_reg < 30 конвертятся в 2 раза лучше — нужно ускорять триггер оффера. Если наоборот — значит, нужно «дать отдохнуть» перед возвратом.

3. **Средний чек по когортам неактивности** — bar chart, avg(purchase_price) по бакетам days_from_reg.
   - *Проблема:* давно ушедшие пользователи могут покупать более дорогие абонементы (осознанное возвращение) или наоборот — дешёвые (проба). Влияет на unit-экономику comeback-канала.

4. **Heatmap: когорта неактивности x CRM-статус** — CR на пересечении. Строки — days_from_reg бакеты, столбцы — CRM/не CRM.
   - *Проблема:* для каких когорт CRM-обработка критична, а для каких — избыточна. Возможно, свежие камбэки конвертятся сами, а для давно ушедших нужен менеджер.

5. **Скорость конверсии по когортам (days_to_purchase)** — box plot или bar chart, avg(days_to_purchase) по бакетам days_from_reg.
   - *Проблема:* свежие камбэки принимают решение быстрее? Если да — для них окно 5 дней с запасом, а для давних — может быть узким.

6. **Кумулятивная конверсия по дням после оффера** — line chart: % конвертировавшихся к дню 1, 2, 3, 4, 5.
   - *Проблема:* валидация 5-дневного окна конверсии. Какой % покупок происходит в день 1? Если 80% покупок совершается в первые 2 дня — окно можно сократить и быстрее переквалифицировать лид. Если конверсия растёт до дня 5 — окно обосновано.

### Tab 4: Соцдем-сегментация — кто возвращается?

Главный вопрос: **какой сегмент аудитории лучше всего реагирует на comeback-оффер?**

**Графики:**

1. **CR по полу** — bar chart (male / female / unknown), объём офферов + CR %.
   - *Проблема:* персонализация оффера. Если женщины конвертятся значимо лучше — возможно, стоит адаптировать коммуникацию или приоритизировать сегмент.

2. **CR по возрастным группам** — bar chart, бакеты: 16-20, 21-25, 26-30, 31-35, 36-40, 41+.
   - *Проблема:* разные возрастные группы по-разному реагируют на возврат. Молодые (16-20) могут быть импульсивнее, взрослые (30+) — осознаннее. Определяет tone of voice в оффере.

3. **CR по городам — top-20** — table: город, кол-во офферов, CR %, средний чек, выручка.
   - *Проблема:* географическая приоритизация. В маленьких городах может быть мало клубов и оффер неактуален. В крупных — высокая конкуренция и люди уходят к конкурентам. Таблица покажет, где comeback работает, а где — нет.

4. **CR по устройству** — bar chart (ios / android / unknown).
   - *Проблема:* если CR на iOS значимо выше — возможно, push-уведомления на Android не доходят или UX покупки хуже. Технический сигнал для продуктовой команды.

5. **Heatmap: пол x возраст** — CR на пересечении.
   - *Проблема:* нахождение «горячих» и «холодных» сегментов. Например, «женщины 26-30» могут быть лучшим сегментом — это портрет идеального comeback-лида для таргетинга.

6. **Heatmap: город x устройство** — CR на пересечении, top-10 городов.
   - *Проблема:* выявление технических проблем по географии. Если в конкретном городе Android-конверсия аномально низкая — возможно, есть проблема с оплатой или UX.

7. **Средний чек по полу и возрасту** — grouped bar chart.
   - *Проблема:* LTV-прогноз по сегментам. Даже если CR одинаковый — сегмент с более высоким чеком ценнее. Помогает приоритизировать CRM-ресурсы.

### Tab 5: Операционная аналитика — ежедневный мониторинг

Главный вопрос: **что происходит прямо сейчас и нужно ли вмешиваться?**

**Графики:**

1. **Офферы за последние 7 дней — daily breakdown** — bar chart с CR % overlay.
   - *Проблема:* оперативный мониторинг. Резкое падение числа офферов может означать сбой в триггерной логике. Резкое падение CR — проблему в продукте.

2. **Таблица: вчерашние офферы по городам** — city, offers count, CRM sent count, ожидаемая конверсия (на основе исторического CR города).
   - *Проблема:* планирование нагрузки CRM-команды. Если вчера было 200 офферов и 60% уходят в CRM — менеджеры знают свою загрузку на сегодня.

3. **Конверсия «незакрытого окна»** — текущие офферы, у которых 5-дневное окно ещё не истекло. Сколько уже купили, сколько ещё в окне.
   - *Проблема:* early signal. Если из вчерашних офферов уже 10% купили в день 1 — прогноз позитивный. Если 0% — сигнал тревоги.

4. **Anomaly detection: CR по дням vs скользящее среднее (30 дней)** — line chart с confidence band.
   - *Проблема:* автоматическое выявление отклонений. Если сегодняшний CR ниже двух стандартных отклонений — нужно разбираться (техническая проблема, изменение оффера, конкуренция).

---

### Tab 6: Unit-экономика и ROI

Главный вопрос: **окупается ли comeback-канал?**

**Графики:**

1. **Выручка vs объём офферов — тренд** — dual-axis: bar (offers) + line (revenue).
   - *Проблема:* масштабируемость канала. Если увеличение объёма офферов не приводит к пропорциональному росту выручки — канал насыщается.

2. **Revenue per offer (RPO)** — SUM(purchase_price) / COUNT(offer_id) по неделям, line chart.
   - *Проблема:* единая метрика эффективности, учитывающая и CR, и чек. Удобно для сравнения периодов и A/B тестов.

3. **Распределение purchase_price** — histogram.
   - *Проблема:* понимание, какие абонементы покупают камбэки. Если большинство берёт минимальный — возможно, нужен upsell в оффере. Бимодальное распределение может говорить о двух разных сегментах.

4. **Средний чек по месяцам — тренд** — line chart.
   - *Проблема:* деградация чека. Если средний чек падает при стабильном CR — клиенты переключаются на более дешёвые тарифы. Сигнал для ценовой политики.

5. **Конверсия и чек по странам** — table: country, offers, CR %, avg check, total revenue, RPO.
   - *Проблема:* кросс-страновое сравнение эффективности. Позволяет выявить страны, где comeback-механика работает плохо и требует адаптации.

## Фильтры дэшборда

- **country** — мультиселект, по умолчанию все страны
- **offer_date** — date range picker, основной фильтр периода
- **city** — мультиселект
- **gender** — мультиселект
- **device_type** — мультиселект
- **send_to_amocrm** — boolean фильтр (CRM / не CRM / все)
- **days_from_reg bucket** — мультиселект для когорт неактивности

---

## Ключевые инсайты, которые дэшборд позволит получить

1. **ROI от comeback-механики** — общая эффективность канала и его вклад в выручку.
2. **CRM uplift** — количественная оценка эффекта от передачи лида менеджеру. Аргумент за/против расширения CRM-команды.
3. **Оптимальный тайминг оффера** — через какое время после регистрации отправлять comeback-оффер для максимальной конверсии.
4. **Валидация 5-дневного окна** — достаточно ли 5 дней или конверсия продолжает расти после.
5. **Портрет идеального comeback-лида** — пол, возраст, город, устройство с максимальным CR и чеком.
6. **SLA для CRM** — допустимая задержка передачи в AmoCRM без потери конверсии.
7. **Географическая приоритизация** — куда направлять CRM-ресурсы и маркетинг-бюджет.
8. **Аномалии и деградация** — раннее обнаружение проблем через оперативный мониторинг.
9. **Ценовая сегментация** — какие абонементы покупают камбэки и есть ли потенциал для upsell.

## Реализация в Superset

- **Dataset:** `dash.leads_comebacks` — единственный dataset для всего дэшборда.
- **Calculated columns** (в Superset или в SQL):
  - `days_from_reg_bucket`: CASE WHEN для когорт неактивности.
  - `age_group`: CASE WHEN для возрастных бакетов.
  - `crm_delay_days`: DATEDIFF(send_to_amocrm_date, offer_date).
  - `is_converted`: CASE WHEN purchase_date IS NOT NULL THEN 1 ELSE 0 END.
  - `revenue_per_offer`: используется как агрегированная метрика.
- **Cross-filter:** включить native cross-filter для интерактивного drill-down между чартами.
